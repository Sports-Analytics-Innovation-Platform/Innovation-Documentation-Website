=== CLAUDE  (2026-09-25 12:10:09) ===
No, nothing gets removed. Each game's play-by-play is pulled, checked, **saved permanently** in the `GameEvent` table, and then used to calculate that game's stats. The part that probably gave the "calculated then thrown away" impression: the stats are calculated from a copy of the plays held in memory during the run, not read back from the database. The save still happens first.

## What happens for each game

The loop is in `ingest_games_and_stats` ([ingest.py:230](apps/ingestion/ingest.py#L230)).

1. **Box score:** one `BoxScoreTraditionalV3` call gives the final score and each player's line. Minutes and plus/minus always come from here.
2. **Game row:** the game is saved, and its type (regular season, play-in, playoffs or finals) is worked out from the game ID.
3. **Play-by-play** (`run_ingestion_batch`, [play_by_play.py:151](apps/ingestion/play_by_play.py#L151)):
   - An `IngestionBatch` record opens as RUNNING. If an earlier run of this game crashed, it picks up the old FAILED batch and resumes from its checkpoint.
   - One `PlayByPlayV3` call fetches every play. The NBA's action names are translated into ours, and each play is checked: correct order, a player we know, an action type we recognise.
   - Rejected plays are only counted, in the batch's `rejectionSummary`.
   - **Accepted plays are written to `GameEvent`** ([play_by_play.py:117](apps/ingestion/play_by_play.py#L117)), with a resume checkpoint after each one.
   - The batch closes as COMPLETED, or as PENDING_REVIEW if you ran with `--review`.
4. **Calculating stats:** `aggregate_player_game_stats` works out points, shooting splits, offensive/defensive rebounds, assists, steals, blocks and turnovers from the in-memory plays.
5. **Merging:** the box score line, the advanced figures and the calculated counting stats are combined, with the calculated stats taking priority. The result is saved as a `PlayerGameStat` row. If a player has no usable plays, their box score numbers are kept instead.
6. **Commit** after every game, so a crash only loses the game in progress.

Before the loop, a few league-wide calls gather the game IDs, plus/minus and advanced stats like usage rate for the whole season segment, so those don't cost one call per game.

## Why the plays are kept

Nothing in the pipeline or the API deletes `GameEvent` rows (only tests and the seed script clear the table). Several features read the stored plays after ingestion:

- **Admin corrections:** fixing a play recalculates that game's stats from the stored plays, and "replay game" does the same for the whole game ([admin-events.service.ts:331](apps/api/src/admin/admin-events.service.ts#L331)).
- **Admin play-by-play panel:** it shows the stored plays.
- **Public API:** `GET /games/:id/events` and the live-events poll return them ([games.service.ts:270](apps/api/src/games/games.service.ts#L270)).
- **Audit trail:** a published stat can be traced back to its batch and the plays behind it.

## What this means for the older seasons

The 2023-24 and 2024-25 regular seasons have no stored plays, so their stats are box-score only. That's most likely because they were loaded before the play-by-play step existed; the migration that switched stats to play-based calculation is dated 2026-09-16.

Calculating without saving is a small change: skip the insert in step 3 and keep the in-memory list for step 4. For those games you'd lose corrections, the play-by-play panel and the events endpoint. That's why I suggested it only as an option for the old postseasons, not as a change for everything.

=== CLAUDE  (2026-09-23 12:49:31) ===
Yes, it's safe to cancel. Press Ctrl+C once and wait for the process to exit.

**Why it's safe:** `ingest.py` only commits at the end of each phase: teams, rosters, bios, the regular season, then the postseason ([ingest.py:419-466](apps/ingestion/ingest.py#L419-L466)). If you cancel partway through a phase, that phase's writes are never committed and Postgres discards them when the connection closes. Nothing is left half-written. Any phase that already finished is kept, and every write in it is an upsert, so the new run simply writes it again. The worst case is a few minutes of repeated NBA API calls.

**Because of that commit pattern, I'd run the new command in chunks.** The whole regular season is written in a single transaction. In one run covering October to June, a crash or dropped connection at game 1,200 loses all 1,200 games. Monthly chunks limit a failure to one month:

```powershell
.venv\Scripts\python.exe ingest.py --season 2025-26 --from-date 2025-10-01 --to-date 2025-10-31
.venv\Scripts\python.exe ingest.py --season 2025-26 --from-date 2025-11-01 --to-date 2025-11-30
# ...one per month...
.venv\Scripts\python.exe ingest.py --season 2025-26 --from-date 2026-04-01 --to-date 2026-06-30
```

The last chunk covers the end of the regular season plus the play-in, playoffs and Finals. Each chunk also repeats the teams and rosters phases, about 30 quick calls, so there's little overhead. Bios only run for players still missing one.

After each chunk you can check its months with the period-only query from earlier. Those games should drop off the list as you go.

=== CLAUDE  (2026-09-23 20:19:02) ===
Correct: re-running doesn't duplicate anything, including re-running a month or overlapping dates. Every data table is written with an upsert keyed on a unique ID, so a second write updates the existing row instead of adding one:

| Table | One row per | Re-running… |
|---|---|---|
| `GameEvent` (plays) | game + play number | overwrites the play in place. The 8 period markers are overwritten too, not doubled |
| `Game` | NBA game id | updates the same game |
| `PlayerGameStat` | player + game | updates the same stat line |
| `Player` / `Team` | NBA player / team id | updates the same row |

`IngestionBatch` is the one table that grows. Each run adds a new batch row per game, by design, because it's the run history, like the three generations you saw for 15 May. Those rows are logs; they don't duplicate plays or stats.

What happens if a run stops partway:
- **Connection drops in the middle of a game.** That game's plays and its batch row are rolled back together, so nothing is half-saved and no stray batch is left behind. Every game finished before it stays saved.
- **The NBA API call fails for a game.** That game's batch is saved as `FAILED`. The next run picks up that same batch and continues it instead of opening a new one. Until then, #184 hides that one game from public pages.

So if you re-run a range you've already done, the only cost is time.

## Why it's faster
The time was going into waiting, not into work. Every database statement is a round trip: your laptop sends it to Supabase in London, then waits for the reply before sending the next. The data is tiny; the waiting is what costs. From your run (26 games in an hour), each trip takes roughly 0.13 seconds.

| | Round trips per game | Waiting per game |
|---|---|---|
| **Before** | ~1,000: two per play (save the play, then save a checkpoint) | ~2+ minutes |
| **Now** | ~35: all plays in one statement, one checkpoint, plus a couple dozen player stat lines | ~5 seconds |

It's like posting 500 letters one at a time and waiting for each reply before sending the next, versus posting them all in one parcel. Postgres does the same work either way; you just stop waiting 1,000 times.

## Why it wasn't done this way from the start
The cost stayed hidden until today, for three reasons:

1. **Development used a local database.** Against `localhost`, a round trip takes about a tenth of a millisecond, so 1,000 of them add up to about 0.1 seconds per game. Nothing looked slow. #181 was checked against 35 real games that way.
2. **Until #181, production pulls barely wrote any plays.** Each game kept only its 8 period markers, so a pull made about 16 play-related trips per game, not 1,000. The per-play cost only appeared once plays were actually being kept, and today's run is the first real production pull with the fixed code.
3. **The per-play checkpoint made sense when it was designed.** It came from the "resume failed batches" feature (16 September), meant to let a crashed game pick up mid-game. But every game is saved as one unit (all its plays or none), so those mid-game checkpoints could never survive a crash anyway. One checkpoint per game gives the same protection.

I should have caught this sooner myself. When you started the run, I said "hours" without working it out. The round-trip cost only became obvious once we had your real pace to measure against.

**The ~5 second figure is still an estimate.** The first few minutes of your next run will confirm it.

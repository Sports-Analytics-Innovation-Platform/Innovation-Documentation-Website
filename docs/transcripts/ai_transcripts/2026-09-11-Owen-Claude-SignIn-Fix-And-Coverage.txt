I found the actual mechanism. Before applying a fix, here's what's going on and the trade-off
involved.

**What's happening:** Your login uses Google OAuth via BetterAuth, and "login link expired" is
BetterAuth's `state_mismatch` error (see
[AuthStatus.tsx:10](apps/web/src/components/AuthStatus.tsx#L10)). Your frontend (Cloudflare Pages)
and API (Render) are on different domains, so the sign-in flow depends on a short-lived `state`
cookie surviving a cross-domain round trip through Google.

Two earlier fix attempts already live in [auth.config.ts](apps/api/src/auth/auth.config.ts#L98-L134)
(cookie lifetime widened to match the 10-min DB record; `SameSite=None` added for prod) — both
correct, both already deployed via `main`. But there's a third cause neither fix touches:
`authClient.signIn.social()` sets that cookie via a cross-origin `fetch()` call
([authClient.ts:17](apps/web/src/lib/authClient.ts#L17), [fetch-
plugins.mjs](apps/web/node_modules/better-auth/dist/client/fetch-plugins.mjs)), not a top-level page
navigation. Browsers with stricter privacy defaults — Safari (blocks 3rd-party cookies by default),
Firefox (Total Cookie Protection, on by default), Brave — silently refuse to persist a cookie set
that way, or partition it separately from how it's read back later. Plain Chrome/Edge with default
settings mostly still works. That lines up exactly with "some people, not others": it tracks
browser/privacy settings, not anything random.

**The reliable fix:** BetterAuth has a first-class escape hatch for this exact cross-domain scenario
— `account.skipStateCookieCheck: true`. It stops requiring that cookie to validate the callback,
relying instead on the random `state` value round-tripped through Google plus the 10-minute DB
record (still checked, still single-use). The trade-off: it removes one defense-in-depth layer
against a narrow "login CSRF" attack (tricking a victim into landing in the attacker's own Google
session) — not credential theft, but worth you knowing about since this is a graded project.

The fully "correct" alternative is putting the frontend and API on a shared custom domain (e.g.
`app.example.com` / `api.example.com`) and using BetterAuth's `crossSubDomainCookies`, which keeps
the cookie check working properly — your own [ADR-003](docs/decisions/ADR-003-hosting-topology.md)
flags this domain question as still open. That needs DNS/infra work outside this repo.

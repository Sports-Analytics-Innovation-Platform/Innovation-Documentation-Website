  Your two questions

  Can we load everything per request, store nothing, and stay under rate limits?
  Yes.
  - Nothing is stored. No tables and no rows, only an in-memory cache.
  - NBA traffic doesn't grow with visitors. Each NBA file is fetched at most
    once per cache period: 10 s while a game is live, an hour once a finished
    game settles, a day for the schedule. Simultaneous requests share one fetch.
    A busy night works out to about 1–2 small requests a second to the NBA's
    CDN.
  - The real risk was our own API. The other public routes check an API key, and
    signed-out visitors all share one site key (100 requests/min, 10,000/day by
    default) that writes a database row per request. A few people polling would
    have hit that limit for the whole site and grown the database. So the live
    routes skip that check, and they only ever fetch games on the NBA schedule,
    so callers can't make the backend fetch arbitrary files.

  How do we avoid slow loads?
  - Repeat requests answer from memory in 3–5 ms.
  - Responses are small: about 2 KB for the game list and 11 KB for one game.
    The NBA's 5 MB schedule and 430 KB play-by-play files never reach the
    browser.
  - First request after the cache empties takes 2–4.5 s. Render's free-tier
    wake-up (30–60 s) costs more, and only a keep-alive ping avoids it.
  - The pages refresh every 15 s while a game is live (60 s otherwise), pause in
    background tabs, and keep showing the last good data if a refresh fails.

  One risk I couldn't test

  Render already can't reach stats.nba.com. I couldn't check whether it can
  reach cdn.nba.com; if it can't, this design won't work in production. The API
  would then return a 503 saying the NBA's server refused the request. The
  cheapest check is to point a temporary free Render service at this branch and
  open /v1/live/games.

  Two things I found while testing the feeds:
  - The NBA's server rejects requests that don't name https://www.nba.com/ as
    the referring page. The backend now sends that.
  - A game that hasn't started also comes back as "refused". The code tells this
    apart from a real block, so an outage shows as an error instead of an empty

  Title: Live tab: live, upcoming and recent NBA games from the NBA's live feed

  What it adds
  - A Live tab with three sections, preseason included:
    - Live: games in progress, with the quarter and clock.
    - Upcoming: games starting in the next 24 hours, with a countdown. A game
      shows "Starting soon" once its start time passes and stays there until it
      tips off.
    - Recent: games that finished in the last 18 hours, with how they ended.
  - A game page (/live/:gameId) with the scoreboard, the last 5 minutes of play
    while the game is live, and the box score split by team.
  - Two public API routes: GET /v1/live/games and GET /v1/live/games/:gameId.

  Design points worth reviewing
  - Nothing is stored. Data comes from the NBA's public CDN on demand and is
    kept only in an in-memory cache, about 0.4 MB measured. There are no
    migrations and no database access at all.
  - The routes skip the session and API-key guards on purpose. Those guards read
    the database on every request, and the API-key guard writes a usage row
    each time. A page that polls every 15 seconds would turn that into constant
    database traffic and use up the site key's rate limit. Traffic to the NBA
    stays flat however many people watch, because every viewer is served from
    the same cached copy and only games on the schedule are ever fetched.
  - This is a bonus feature, outside the brief's core scope. The stats are
    NBA-provided, not derived from our event data, and the page says so.

  Verified
  - Render can reach the NBA's live feeds. We tested it with a temporary Render
    service on this branch. Note that Render is blocked from stats.nba.com,
    which is a different server.

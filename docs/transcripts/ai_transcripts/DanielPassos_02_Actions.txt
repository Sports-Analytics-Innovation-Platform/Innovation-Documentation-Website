## Issues found
### Critical
- Four Factors predictions for completed games leak the selected game and future games. `predict_games.py` computes one set of averages from every completed game, then applies those averages to every historical game. Consequently, an early game’s “prediction” includes its own box score and every later completed game. This directly contradicts the module’s claim that completed predictions reflect only what was knowable beforehand.
- The regression path also uses same-game performance as an input feature. `four_factors.py` trains each row using that team’s realized eFG%, turnover rate, and free-throw rate from the game whose margin is the target. Those figures are unavailable pregame. Using an opponent season average does not remove leakage from `team_row`. Training and inference also use different feature definitions: same-game factors during fitting versus full-history averages during prediction.
- Historical top-scorer predictions use future games. `game-detail.service.ts` excludes only `gameId`; it does not constrain `game.gameDate < targetGame.gameDate`. Opening an older game therefore incorporates player performances occurring after that game. The added test verifies exclusion of the target game but never adds a later game, so it misses this defect.
### Important
- The Predictions page reports only the home team’s probability, even when the away team is favored. It can display text such as “LAL 30% win” instead of showing the away team at 70%. The detail page handles this correctly, creating an inconsistent API presentation.
- Four Factors “season averages” pool all seasons because neither the SQL query nor averaging groups by season. Elo likewise processes the entire database without season reset/regression. With multi-season NBA data, predictions will combine unrelated seasons while documentation calls them season averages.
- Team box-score attribution relies on each player’s current `teamId`. A traded player’s older statistics will be attributed according to their current roster, not necessarily the team they represented in that game. The present schema lacks team-at-game data, so this needs an explicit data-model decision.
- There are no Python tests for Elo ordering, Four Factors leakage, chronological cutoffs, regression features, multiple seasons, or prediction persistence. The core analytics implementation is therefore unprotected despite being the PR’s central functionality.
### Minor
- `GamePrediction.gameId` has both `@unique` and `@@index([gameId])`, producing a redundant index.
- The relation uses the default restrictive delete behavior. Deleting a game now fails unless its prediction is deleted first. The test reset was updated, but other game replacement/cleanup workflows need to account for this or use deliberate cascading behavior.
- The court labels the visualization a “predicted starting five,” although the backend selects top projected scorers, not predicted starters. Its slot assignment also places players into fixed guard/forward/center coordinates based on array order rather than ensuring their assigned slot matches their actual position.
- `createdAt` is updated on every upsert, so it behaves as “last generated at,” not creation time.
- The structural API/schema additions were not added to `docs/PROJECT_OVERVIEW.md`, despite that document requiring structural changes to update it.

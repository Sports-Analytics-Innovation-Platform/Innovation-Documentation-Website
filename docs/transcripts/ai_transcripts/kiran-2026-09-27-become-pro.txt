SESSION SUMMARY
========================================================================

GOAL
Add a "Become Pro" feature: a player logs their own season, gets a
monetary value computed by real algorithms (not AI) from data the
project already collects, compares themselves with NBA players, and can
update their data. The first design also had a value leaderboard and a
"#N" rank badge; that was later removed (see "Re-scope").

KEY DECISIONS (the user's answers)
- Value anchor: the published NBA rookie salary scale. Nothing in the
  repo or nba_api has salary data, so the model projects a draft pick
  and the pick is priced on the scale.
- Input: per-game box scores; the season line is derived, never typed.
- Competition level: required, and it scales the value.
- Valuation timing: the API values a season on every write, so the
  figure appears the moment the 10th game is logged.
- Data for testing: pull real NBA data locally with nba_api (bulk
  copying from production was blocked by the permission system and was
  not attempted again).
- Visibility: private to each user.

WHAT WAS BUILT
1. Web (apps/web): the /become-pro page; season setup, editing,
   switching and deletion; fast game entry with edit and remove;
   box-score validation that blocks impossible lines and warns on
   mismatched points; season line, scoring chart and traits radar;
   projected value card (pick, dollars, range, history, provenance,
   drivers); comparison radar against three NBA rookies, plus players
   drafted at the projected pick; a Become Pro card on Home and
   Profile; an eighth nav link.
2. API (apps/api/src/become-pro): session-guarded /v1/me/become-pro
   routes; season line derived with the same code as NBA players;
   valuation applied on every write and refreshed when a newer model
   exists; comparables from the model's own training set, restricted
   to rookie regular seasons and published games; Prisma models and
   one consolidated migration.
3. Model (apps/valuation): trains a least-squares model on real NBA
   rookie seasons (rookie season taken from draftYear, published games
   only), mapping points, rebounds, assists and true shooting to a
   draft pick, and stores the fitted model, rookie scale, level
   factors and comparable index as one row the API applies.

RE-SCOPE (26 Sep)
The user removed the leaderboard and all comparison between users:
Become Pro is now you versus NBA rookies only, private to each user.
With nobody else seeing a user's figures there is nothing to verify,
so the evidence upload, reliability score and admin review queue were
removed too, and the Supabase evidence bucket is no longer needed.

TESTING
- Live browser run: 65 of 65 checks passed, with no console errors.
  It used headless Edge with the real web app, API, local Postgres
  filled from nba_api, a model trained on that data, and two real
  signed-in users.
- Automated: API 974 tests (31 Become Pro end-to-end), web 717 tests
  (90.2% line, 84.2% branch coverage), valuation 24 tests; typecheck,
  lint and production build clean.

BUGS FOUND AND FIXED DURING TESTING
- The rookie scale was wrong (pick 1 about 11% too high) and a year
  stale. It was replaced with the published 2026-27 figures and
  cross-checked against 2025-26 (every pick rose exactly with the
  salary cap).
- The value range could exceed what pick 1 is paid; it is now clamped
  to the scale.
- The value history repeated identical points; runs now collapse.
- The competition-level sentence was printed twice on the value card.
- On phones the value card was buried at the bottom and the games
  table's headers ran together; the stat inputs wrapped on desktop.
- Earlier in the build: the model used the earliest season on record
  as the rookie season (wrong for veterans), comparables ignored the
  published-games rule, and the radar plotted the raw line while the
  similarity used the level-adjusted one. All fixed.

PRODUCTION
- The user merged the branch to main; Render applied the migration.
- The valuation model was trained against production on 27 Sep from
  its own branch: 140 real rookie seasons (the 2023-2025 draft
  classes), MAE 10.9 picks, rank correlation 0.54, model
  c40a1d20-5001-4ec1-8aac-dad196768e61. Nothing else in production
  was written.
- A CI failure on the push was a network error during npm ci, not the
  code; the runner is a Docker container on the user's machine.

OPEN ITEMS AT HAND-OFF
- Retrain production once the 2026 draft class has about 20 games, and
  every summer when the new rookie scale is published.
- CI runs no Python tests for any service.
- apps/api/.env lacks DIRECT_URL and has a placeholder SUPABASE_URL
  (local only).
- Ingestion keeps only players on current rosters, which leans the
  model towards rookies who stayed in the league.

## What I built

**Schema + migration** — `ProspectSeason`, `ProspectGame`,
`ProspectEvidence`, `ProspectValuation` plus two enums, in
[schema.prisma](apps/api/prisma/schema.prisma) and [20260923000000_add_b
ecome_pro](apps/api/prisma/migrations/20260923000000_add_become_pro/migr
ation.sql). Prisma emitted two unrelated statements from local dev-DB
drift (a `DROP INDEX` on `IngestionBatch`, a `DROP DEFAULT` on
`IngestionSchedule`); I stripped them and documented why in the
migration header — left in, they'd have silently altered the ingestion
tables on every other environment.

**One derivation, not two.** I extracted `deriveSeasonAverages` into
[season-averages.ts](apps/api/src/players/season-averages.ts) and made
`StatsService` delegate to it, so a prospect's season line comes from
the *same* code as an NBA player's. Re-implementing it would have given
two definitions of "true shooting" that could drift — and a prospect's
figures would stop being comparable with the pros they're measured
against, which is the whole feature. Safe to do: `DerivedSeasonAverages`
had no importers outside that file.

**Three controllers over two services**, split by guard: public reads,
owner writes, admin review. Notable choices —
- Validation reuses [stat-anomalies.ts](apps/api/src/admin/stat-
  anomalies.ts) rather than restating it; [prospect-box-
  score.ts](apps/api/src/become-pro/prospect-box-score.ts) only adds
  *severity*, so a points total that disagrees with its own splits is
  recorded, not refused.
- `PATCH` on a game clears its `evidenceId`. Without that, reliability
  is farmable: log a modest game, get it verified, edit the numbers
  upward, keep the credit.
- Ownership failures return **404, not 403** — a 403 would confirm the
  id is real but somebody else's.
- Ranking happens over the whole board before filtering, so a level
  filter can't renumber prospects from 1 and disagree with the header
  badge.

**`apps/valuation/`** — Python, house pattern, numpy only, no LLM. The
README states plainly what the model *doesn't* do: it isn't trained on
"amateur season → draft slot" because no such dataset exists here. It
fits draft slot against NBA **rookie** production and inverts it, and
the three real limitations of that are written down rather than buried.

# Become Pro — user-submitted seasons, player valuation, and a value leaderboard

> **Scope: `apps/web` only.** The backend is implemented separately from the API
> contract in §4. Everything here builds and tests with the backend absent.

## 1. Context

The platform only knows about NBA professionals. Every published statistic derives from
real `GameEvent` rows, and the only leaderboard ranks people calling game winners against
the Elo model. A user can follow players, save lineups and make picks — but cannot put
*themselves* into the system.

**Become Pro** closes that gap: a player logs their own games, the platform derives their
season line the same way it derives a pro's, prices that season against the real NBA rookie
salary scale, and ranks them against everyone else who has done the same.

### The premise that had to change

The request assumed we could "call upon the existing APIs to find monetary value of pro
players." **We cannot.** There is no salary, contract or market-value data anywhere in this
repo, and `nba_api` exposes none. The only dollar figure is `PlayerPrediction.salary`, which
[predict.py:227-235](apps/optimizer/predict.py#L227-L235) computes as
`$3000 + predictedFantasyPoints × $160` clamped to `$3k–$11k`; both the Python and
[schema.prisma:501-504](apps/api/prisma/schema.prisma#L501-L504) label it synthetic DFS
pricing and "not a real market price."

So the valuation anchors on the **published NBA rookie salary scale** — a small, fixed,
public table shipped as a constant, no scraping. The model maps a season line to a projected
**draft slot**; the slot maps to real rookie-scale dollars. That is also the most honest
framing of the goal: not "what is this player worth today" but "what would they sign for
entering the league."

### Decisions taken

| Decision | Choice |
| --- | --- |
| Value anchor | Real NBA rookie scale; stats → projected draft slot → dollars |
| What a user submits | **Per-game box scores**; the season line is *derived*, never typed |
| Competition level | Required per season, and it **scales** the valuation |
| Trust | Public, labelled self-reported, minimum-games floor on the board |
| Verification | Per-game evidence upload driving a **reliability score** |

Per-game entry is deliberate: it preserves the founding rule that every published statistic
traces back to per-game records (README, opening paragraph), and it lets the derived line be
shaped exactly like `SeasonAverages` — so `PointsTrendChart`, `Sparkline`,
`PlayerTraitsRadar` and `ComparisonTraitsRadar` all work on a user's season with **no new
chart code**.

### 4.3 Derivation rules — read this carefully

`seasonAverages` **is the existing `SeasonAverages` type, unchanged.** Do not widen it; the
three shooting percentages are non-nullable `number` at
[types/nba.ts:56-62](apps/web/src/types/nba.ts#L56-L62) and widening them breaks
`PlayerProfilePage`, `SeasonSplitsTable` and every `advancedStats` caller.

Mirror [stats.service.ts:182-195](apps/api/src/players/stats.service.ts#L182-L195) exactly:

- `percentageOf(made, attempted)` → **`0` when `attempted === 0`**, else
  `round((made / attempted) * 100)`. Never null.
- Percentages come from **season totals**, never by averaging per-game percentages —
  "a 1-for-1 night and a 5-for-20 night average to 52.5% but are really 6-for-21."
- `round` is one decimal; `assistToTurnoverRatio` is two.
- `trueShootingPercentage` uses the 0.44 free-throw possession weight, `0` when attempts are 0.
- `assistToTurnoverRatio` is `null` when turnovers are 0 (already nullable).
- `plusMinusPerGame`, `usagePercentage`, `offensiveRating`, `defensiveRating` are **always
  `null`** — amateur box scores don't carry them, and a zero would be a real measurement.

**A 0% from zero attempts is meaningless but type-legal.** The UI suppresses it by checking
`fieldGoalsAttemptedPerGame === 0` and rendering `NO_VALUE`, *not* by making the type
nullable.

Other rules the API owns:
- `minimumGamesRequired` defaults to **10**, echoed in every payload; the client never
  hardcodes it. Rationale mirrors `MINIMUM_CALLS_REQUIRED = 5`
  ([leaderboard-ranking.ts:18](apps/api/src/analytics/leaderboard-ranking.ts#L18)).
- Ranking is **dense**, as `rankLeaderboard`. Order: `projectedValueUsd` desc → more
  `gamesLogged` → higher `verifiedCoverage` → `username` for determinism.
- **`PATCH /games/:gameId` resets that game's `evidenceId` to `null` and its evidence row to
  `PENDING`.** Without this, reliability is farmable: log a modest game, get it verified,
  then edit the numbers upward while keeping the verified flag.
- `ProspectEvidence.fileUrl` is **`null` for anyone who is not the owner or an admin.** A
  scorecard carries other people's names; the public gets the status, never the file.

### 4.5 Where the valuation model lives

`apps/valuation/` — a Python service in the house pattern of `apps/optimizer` and
`apps/predictor`: `db.py`, `value_prospects.py`, `rookie_scale.py` (the fixed public table as
a module constant keyed by scale year), `level_factors.py` (each factor carrying a documented
`basis` string), and co-located `test_*.py`. It writes valuation rows Nest only reads.
Dependencies: `psycopg2-binary`, `numpy`, `python-dotenv`, `pytest` — adding sklearn needs
justifying, per house style. **No LLM anywhere in the path.**

The model **inverts NBA rookie production → draft slot** rather than fitting on amateur
lines, because the repo has no amateur training data. Training set: players with non-null
`draftYear` + `draftNumber` having a rookie season in `PlayerGameStat`. Report MAE and
Spearman on a chronological split in the module docstring, exactly as
[predict.py:12-55](apps/optimizer/predict.py#L12-L55) does. **`apps/valuation/README.md` must
state this inversion plainly** — it is the honest limit of what the figure can claim.

## 6. Presenting the value honestly

The figure is never a bare number:

```
PROJECTION · SELF-REPORTED          ← font-mono text-[9px] tracking-[0.1em] text-locker-ink-muted
#12  KIRAN                          ← ProRankBadge + display name
Slot 18            $4.37M           ← font-display tabular-nums; SLOT FIRST
Range $3.1M – $5.9M                 ← always shown, never suppressed
```

then, in words: *"Projected from 14 self-reported games at NCAA D2, translated by a 0.62
level factor against the 2025-26 rookie scale. This is a projection of a published draft-slot
salary, not an offer and not a market price."*

- **The slot is the object; the dollars are its consequence.** The scale is public and fixed,
  so the model's actual claim is the slot. Leading with `$4.37M` would overstate what was
  computed — the same discipline that made `PlayerPrediction.salary` carry its label.
- **`rookieScaleYear` is always printed**, so the figure cannot go silently stale.
- **`levelFactor` + `levelFactorBasis` are printed as an assumption**, not a fact.
- **`drivers[]` are server-authored** and rendered verbatim.
- **Below the floor there is no figure at all** — `null` slot and value, and the card renders
  *"3 more games needed — minimum 10 to be valued and ranked"*, the same shape as
  [LeaderboardCard.tsx:104-108](apps/web/src/components/home/LeaderboardCard.tsx#L104-L108).
- **Nothing renders `0` for absent.**
- **"Self-reported" appears wherever a figure does** — not once at the top of the page.

**Reliability ladder.** A word carries every step; size and colour only reinforce:

| Tier | Headline | Micro-label |
| --- | --- | --- |
| `STRONG` (≥70% verified) | `font-display text-[34px]`, narrow band | `PROJECTION · SELF-REPORTED` |
| `PARTIAL` | same size | `PROJECTION · PROVISIONAL` |
| `UNDOCUMENTED` | point estimate demoted to `text-[20px] text-locker-ink-muted`; **the range becomes the headline** | `UNVERIFIED ESTIMATE` |

The server genuinely widens the low/high band as coverage falls, so the demotion reflects a
real change in model confidence rather than styling.

> **UI wording:** the label is **"Reliability"**, as asked, with a one-line subtitle stating
> exactly what it measures — *how much of this line is backed by verified documents* — since
> it measures documentation, not truth. The code namespace is `ProspectReliability` /
> `prospectValue.ts` to stay clear of `lib/reliability.ts`.

**Comparables** render through `ComparisonTraitsRadar` with the prospect passed **first**, so
it takes `COMPARISON_PLAYER_COLORS[0]` (`--color-locker-leather`) and the existing legend
names each series in words. Beneath it, `slotAlumni` turns an abstract figure into
*"Pick 24 — Josh Hart, 2017"*, each linking to `/players/:id`.

**Rank absence** is always explained, never a silent gap. `rankState` distinguishes
below-the-floor (with "6 of 10 logged" as a link), awaiting-valuation, and hidden. The header
badge renders nothing; page surfaces render the word **"Not yet ranked"** plus the reason —
a silently absent badge on Profile reads as a bug, the word reads as a state.

## 7. Testing

Coverage thresholds of **80% on lines/statements/functions/branches are enforced in CI**
(`src/components/ui/**` excluded), so every new non-`ui` component needs a spec.

**Buildable before the backend exists:** every component reads through `becomeProApi.ts`, and
every spec replaces it with `vi.mock("@/lib/becomeProApi", …)` — the pattern
[LeaderboardCard.spec.tsx:7](apps/web/src/components/home/LeaderboardCard.spec.tsx#L7) uses.
Nothing touches `fetch` or a server.

Plus a **contract pin**: `becomeProApi.spec.ts` stubs global `fetch` and asserts URL, method,
headers and serialised body verbatim (the `meApi.spec.ts` style), and typed fixtures in
`src/test/becomeProFixtures.ts` fail `tsc` if the backend's shape drifts.

**Meeting the branch gate:** push conditionals down into the small components (each cheap to
drive through every state from a mocked resolver); keep the two pages compositional as
`HomePage.tsx` is; `prospectValue.spec.ts` and `boxScoreValidation.spec.ts` are pure-function
near-100% coverage that offsets the pages.

Representative cases:

- `prospectValue.spec.ts` — `deriveSeasonAverages([])` → `gamesPlayed: 0`, percentages `0`,
  `assistToTurnoverRatio` / `plusMinusPerGame` / `usagePercentage` / ratings all `null`;
  `fieldGoalsAttempted: 0` → `fieldGoalPercentage === 0` **and** the card suppresses it;
  percentages from totals not averaged rates (6-for-21, not 52.5%); `formatProjectedValue(null) === "—"`;
  `formatDraftSlot` across `null` / `1` / `30` / `31` / `61`; every `CompetitionLevel` has a label.
- `boxScoreValidation.spec.ts` — `fgm 6 / fga 4` blocks; `POINTS_MISMATCH` warns but allows save.
- `ProspectValueCard.spec.tsx` — ranked+`STRONG` renders figure/slot/range/"self-reported";
  below floor renders **no dollar figure** and "3 more games needed"; `UNDOCUMENTED` promotes
  the range; signed out → `expect(screen.queryByText(/\$/)).toBeNull()`; `drivers[]` render verbatim.
- `ProspectLeaderboard.spec.tsx` — mirrors `LeaderboardCard.spec.tsx` case for case: ranks best
  first, real `columnheader`s, marks your row **in words** (the analogue of its `benchmark`
  test), explains the floor, empty board shows the invitation, `compact` hides pager+search.
- `SeasonEntryPanel.spec.tsx` — invalid row never calls the mutation; the derived line moves
  as a row is typed; `ApiError` envelope text surfaces; delete is two-click.
- `EvidenceUploader.spec.tsx` — bad mime and oversize both error without calling `postFormData`.
- `ProRankBadge.spec.tsx` — `null` → `container.firstChild === null`; a number → `#12` with an
  accessible name.
- Pages — signed-out, own-no-season, own-below-floor, own-ranked, another prospect (assert edit
  affordances **absent**), load error with working Retry, each ending in
  `await expectNoAccessibilityViolations(container)`.
- Charts — assert `role="img"` and that the `aria-label` names the series in words, as
  [PointsTrendChart.tsx:77](apps/web/src/components/PointsTrendChart.tsx#L77) does.

**No timers.** `useCountUp`/`ModelExplainer` already fail under full-suite load and pass alone;
nothing here is timer-driven. The board's search uses `useDebouncedValue`, exercised with
`vi.useFakeTimers` in that one spec only.

## 10. Risks

1. **The 8th nav link may not fit at `lg`.** Nothing in jsdom can answer this — it needs the
   browser check in §9.7, with the `lg`→`xl` fallback (and its 1024–1279px cost) as the
   documented remedy.
2. **The rookie-scale table goes stale annually.** Mitigated by echoing and printing
   `rookieScaleYear`, but somebody must update `apps/valuation/rookie_scale.py` each summer and
   nothing will warn them.
3. **Public usernames on self-reported figures is a moderation surface** — fabricated
   prospects, abusive team/opponent names, and **real minors' names if `HIGH_SCHOOL` is
   enabled**. No reporting or takedown path is in scope. This is a policy decision to make
   before launch, not a frontend one.
4. **`deriveSeasonAverages` can drift from the API's authoritative derivation.** Mitigated by
   using it *only* for the unsaved local preview and re-reading the server figure after every
   mutation — but §4.3's rules must be honoured on both sides.
5. **Page-level branch coverage is the likeliest CI failure.** The mitigation must be followed
   during the build, not retrofitted.
6. Widening `ComparisonTraitsRadar`'s prop removes the type-level guarantee that entries are
   real NBA players; if someone later reads `player.headshotUrl` there it fails only for
   prospects. Hence the contract comment at the prop.

### Deferred

The **what-if overlay** (`StatTile`'s edit mode over the derived line, POSTed to a
`/valuation-preview` endpoint returning `basis: "HYPOTHETICAL"`) is a natural fit for existing
machinery but is **not one of the asks**, and it forces the model to be callable at request
time — which breaks the "Python writes, Nest reads" pattern and needs a stored-coefficients
row to resolve. Deferred to a follow-up. If it ships, the value must stay model-computed: a
browser-side multiply by `levelFactor` would publish a figure no model produced.

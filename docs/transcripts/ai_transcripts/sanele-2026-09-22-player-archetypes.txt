Yes — both tweaks are possible, and the first one is arguably *better* than what the doc currently proposes. Nothing is built yet (no `apps/similarity`), so this is a design change, not a refactor.

## "5 similar players" — trivial

Pure parameter change. `n_neighbors=6` → `5`, the `rank Int // 1..6` comment in `PlayerSimilarity`, the fixtures, and the connector lines on the cluster map. Zero effort delta, and 5 cards lay out better in a row than 6.

## "3 relevant archetypes" — already half-designed, and it fixes a stated risk

§5.1 already recommends fitting a GMM for soft membership, and §7.2 already stores `membership` as Json. Showing the top 3 is just reading that Json instead of leaning on `primaryLabel`. What it changes:

**It resolves rather than creates problems.** §6 lists "tweeners get a misleading hard label" as a risk and §10.4 gives direct evidence for it — Athlore's own hand-curated taxonomy puts Jordan, Kobe and Durant under *two* archetypes each and Pippen under two. A top-3 display is the honest shape for the data. It also takes pressure off §5.3's label iteration (the most subjective, judgement-heavy half day in the estimate), because a slightly-wrong second or third label reads as nuance rather than as the model being wrong about a player.

**It makes the face-validity test in §10.7 actually passable.** "Does Gobert land in *defensive anchor*" is a coin flip against *traditional big* on box-score features. "Is *defensive anchor* in Gobert's top 3" is a test that can reasonably hold and still catch a broken model.

**Three things you'd need to decide, none of them blockers:**

1. **"Up to 3", not exactly 3.** If a player is 92/5/3, printing the second and third is noise dressed as insight. A floor (show a component only above ~10–15%) gives you "one archetype" for specialists and three for genuine tweeners, which is the truthful answer in both cases.

2. **`k` still shouldn't be 10.** §10.4's argument holds — but note that showing 3 of `k=6` means you're showing half the taxonomy for every player. The floor in (1) handles it; it's just a reason to land nearer the top of §5.1's 6–9 range.

3. **The percentages become user-facing, which raises the bar on the GMM.** Today they're a display nicety; under this tweak they *are* the feature. Two consequences: fit the GMM with `covariance_type='diag'` or on the PCA-reduced ~5 dims (full covariance over 13 features with ~300 eligible players is badly over-parameterised, and you'd get overconfident junk posteriors); and treat the numbers as an *ordering*, not calibrated confidence — with a 15-game sample, "68.4%" is false precision. Rounding to a bar, or wording it as "Mostly stretch big, some traditional big", is more defensible than three decimals.

**Does K-Means survive?** You could drop it — GMM's argmax gives you the hard label the cluster map needs for point colour and hulls. Keeping K-Means is still worth it as the GMM initialiser (standard practice, and it makes the seeded-determinism story in §6 easier), but it stops being the headline model. Worth a line in the doc either way.

**Schema delta:** none required. `membership` Json + `primaryLabel` covers it; the API sorts and thresholds. If you'd rather not sort at read time, an ordered `topArchetypes` Json array is a cheap addition.

**Effort:** roughly neutral. Slightly less label-iteration time, slightly more frontend (a 3-row membership component instead of a badge). The ~8–9 day total in §8 stands.

## The mechanism

Names can't be keyed on cluster id — K-Means renumbers arbitrarily on every fit. Our own runs prove it: the rim-running bigs were cluster 0 at k=6, cluster **6** at k=8, cluster **0** again at k=9. A names file keyed on the number would relabel the league on a re-run and look perfectly healthy doing it.

So names are stored against the **centroid** — the shape of the player at the middle of the group — in [archetype_labels.py](apps/similarity/archetype_labels.py). Your workflow:

```
python explore_fit.py --k 9 --emit-labels archetype_labels.py
```

That writes the file with all nine centroids filled in and names as `TODO name cluster N`, each commented with its size and closest players. You replace the nine strings. That's the whole manual step — you never touch a vector.

On re-fit, [labeling.py](apps/similarity/labeling.py) standardizes your stored centroids against the new fit and matches them one-to-one (Hungarian, so a name is never used twice). Centroids are stored in **real units**, not z-scores, because z-scores drift when the roster pool changes but "83 inches, 1.6 blocks per 36" doesn't. A cluster too far from everything stays `Unnamed archetype` rather than getting a stretched name — that's the signal that you need to name something new. `--emit-labels` refuses to overwrite an existing file, so a re-run can't silently discard your names.

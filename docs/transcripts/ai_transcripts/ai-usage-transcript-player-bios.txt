CommonPlayerInfo — Documentation
What it is
A per-player bio/profile endpoint. Confirmed via expected_data and a real live call: returns three separate result sets per request — CommonPlayerInfo (the bio fields), PlayerHeadlineStats (current PTS/AST/REB/PIE), and AvailableSeasons. .get_data_frames()[0] gives you the bio table specifically — same "don't assume index order" caveat as BoxScoreSummaryV3, worth checking expected_data if you ever need the other two.

Keyed by player_id (not game_id) — comes from the static players lookup, same ID used everywhere else (headshots, play-by-play personId, box scores).

Basic fetch, scoped to your chosen fields
python
from nba_api.stats.endpoints import commonplayerinfo
from nba_api.stats.static import players

FIELDS = [
    'PERSON_ID', 'FIRST_NAME', 'LAST_NAME', 'BIRTHDATE', 'SCHOOL', 'COUNTRY',
    'LAST_AFFILIATION', 'HEIGHT', 'WEIGHT', 'SEASON_EXP', 'JERSEY', 'POSITION',
    'ROSTERSTATUS', 'GAMES_PLAYED_CURRENT_SEASON_FLAG', 'TEAM_ID', 'TEAM_NAME',
    'TEAM_ABBREVIATION', 'TEAM_CODE', 'TEAM_CITY', 'FROM_YEAR', 'TO_YEAR',
    'DRAFT_YEAR', 'DRAFT_ROUND', 'DRAFT_NUMBER', 'GREATEST_75_FLAG',
]

def fetch_player_profile(player_id: int) -> dict:
    info = commonplayerinfo.CommonPlayerInfo(player_id=player_id)
    df = info.get_data_frames()[0]
    return df[FIELDS].iloc[0].to_dict()

lebron_id = players.find_players_by_full_name("LeBron James")[0]['id']
profile = fetch_player_profile(lebron_id)
profile
Field-by-field notes
Field	Notes
PERSON_ID	Join key — same ID as personId in play-by-play, player_id in static lookups
FIRST_NAME / LAST_NAME	Plain strings — but recall the accent issue found in play-by-play (Jokić vs Jokic). Worth checking whether LAST_NAME here matches the accented or stripped form, since it may differ from what you saw in description text
BIRTHDATE	Comes back as a full ISO timestamp string (e.g. "1984-12-30T00:00:00"), not a bare date — needs parsing before storing as a Date column
HEIGHT	String, not numeric — feet-inches format like "6-9". Needs parsing (split on -, convert to total inches or cm) if you want to sort/filter/compare by height
WEIGHT	Also a string (e.g. "250"), representing pounds — confirm it's always numeric-as-string and not sometimes blank
SCHOOL / COUNTRY / LAST_AFFILIATION	Free text, can be blank for some players — don't assume non-null
SEASON_EXP	Years of NBA experience, integer
JERSEY	String (jersey numbers can have leading behavior worth checking — e.g. is it "6" or "06"?)
POSITION	Free text like "Forward", "Guard-Forward" — not a fixed enum as far as confirmed; worth checking the actual distinct values across a few players before treating it as a closed set
ROSTERSTATUS	Active/inactive roster flag
GAMES_PLAYED_CURRENT_SEASON_FLAG	Confirmed present in the live response but wasn't in your earlier offline expected_data check — a field that only shows up with a real network call, good example of why live verification still matters even after checking expected_data
TEAM_ID / TEAM_NAME / TEAM_ABBREVIATION / TEAM_CODE / TEAM_CITY	Player's current team only — this endpoint doesn't give team history. TEAM_ID is 0 or blank for a player with no current team (retired, unsigned) — unverified, worth checking
FROM_YEAR / TO_YEAR	Career span — TO_YEAR for an active player is presumably the current season, not blank; worth confirming
DRAFT_YEAR / DRAFT_ROUND / DRAFT_NUMBER	Likely returns the string "Undrafted" for undrafted players rather than a null/numeric value — this is a known nba_api behavior pattern, but not yet verified against a real response in this notebook. Worth testing on a known undrafted player (e.g. someone like Fred VanVleet) before assuming these columns are safe to store as Int? in the schema — if they're sometimes the string "Undrafted", they need to be String? instead, or normalized at ingestion time
GREATEST_75_FLAG	Boolean-ish flag for the NBA 75th Anniversary team — niche, low priority
Fetching responsibly
This is the part worth being deliberate about, because it's structurally different from play-by-play:

This is a per-player call, not a bulk one. There's no "give me all players' profiles in one request" — a full profiles feature means one CommonPlayerInfo call per player. For even a single team's roster (~15 players) that's 15 sequential requests; for the whole league it's 500+.
stats.nba.com has no documented rate limit, but it does throttle/block bursty traffic — the same header-spoofing that gets you past the initial block (Section 1) doesn't make you immune to being rate-limited if you hammer it with rapid concurrent requests. nba_api doesn't add any automatic delay between calls — that's on you.
Practical guidance: if you loop over many players, add a small delay between calls (e.g. time.sleep(0.6)), and don't parallelize aggressively. This is exploratory advice based on how these APIs generally behave, not something empirically tested in this notebook — worth a real test (e.g. loop over one full roster, watch for errors/blocks) before trusting it at scale.
This maps directly onto the Section 1 architecture decision. Player profiles are close to static — they don't change mid-game. That makes this a strong candidate for batch/offline ingestion (Option C): pull once, store in Postgres, refresh occasionally (daily/weekly), rather than calling stats.nba.com live every time someone views a profile page in the app. Fetching this live on every page load would be both slow (a full network round-trip per profile view) and exactly the kind of repeated-request pattern that risks rate-limiting.
Schema implication
Given the HEIGHT/WEIGHT/DRAFT_YEAR format quirks above, the Player table's ingestion step (not just the raw column pull) needs light normalization — same principle as the assistPersonId parsing: clean once at write-time, store the cleaned form, don't parse on every read.

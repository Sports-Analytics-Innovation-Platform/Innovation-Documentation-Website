## What this closes

The brief's own words: *"This derivation is the core of the platform... Every statistic it publishes
should be derived from a record of the individual events."* That was false before this PR —
`PlayerGameStat` was written straight from the boxscore endpoint; `GameEvent` held two fake bookend
rows per game and nothing else. Now:

- Real per-play data (`PlayByPlayV3`, previously unused anywhere in the codebase) is fetched,
schema-validated, and written as real `GameEvent` rows.
- `PlayerGameStat`'s counting stats (points, shooting splits, rebound split, assists, steals,
blocks, turnovers) are **aggregated from those events**, not the boxscore — a genuine two-stage
derivation, matching what `stats.service.ts` already claimed in a comment but didn't actually do.
- Every ingestion run is recorded as an `IngestionBatch` (accepted/rejected counts, rejection
reasons) — a real, honest "submission" record a stat traces back to, scoped to what this project
actually is (one automated pipeline, not many human submitters).
- Two more named Basic-tier gaps closed: `GET /v1/games/:id/events` (read events through the API)
and `GET /v1/players/export` (CSV download of a filtered slice).
- Also caught and fixed a real latent bug: `backfill_advanced_stats.py` would have silently
overwritten event-derived rebound splits with older data on every re-run.

**73 tests total** across the two new pure Python modules and the new API endpoints, all passing;
full API typecheck/lint/unit-suite green.

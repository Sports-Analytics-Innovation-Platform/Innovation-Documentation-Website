## Findings that cost marks, most serious first
1. **A Gitea runner token is committed on `main`.** The file is `ci-runner/data/.runner`; it came in
via direct commit `020f4c6` on 12 Sep. `security.md` says it "never reached `main`". Unregister the
`kiran-backup` runner in Gitea, remove the file, add `ci-runner/` to `.gitignore`, and correct the
doc.
2. **Live data reads take 2.6–4.5 s, even when cached.** `/health` through the same path takes ~0.5
s, so the extra time is server-side. The most likely cause is the API-key check: it runs 3 database
queries plus a usage-log write on every request before the cache is consulted, and the site's own
proxy always sends a key. So the "0 database statements on repeat" claim in `performance.md` isn't
true in production. Keeping key lookups and rate-limit counters in memory should fix this.
3. **No human submission path.** The brief's Basic tier is built around approved submitters
uploading a file or posting events and being told why a submission was rejected. Here, data only
arrives through the nba_api pipeline. `feature-tiers.md` marks this ✅; a strict marker won't.
4. **Docs overclaim in places markers will check:**
   - `git-methodology.md` says pushes to `main` are blocked and reviews are mandatory. In fact
`main` has no branch protection, 21 commits went straight to `main`, only 4 of 107 merged PRs have a
recorded approval, and 28 were merged by their own author.
   - Custom-statistic "versioning" just increments a counter and overwrites the old formula, so a
figure computed under an earlier version can't be reproduced.
   - The README calls the project a "scaffold".
5. **Swagger:** 0 response schemas, 29 of 114 operations have no description, and catch-all routes
appear in the spec.
6. **Board hygiene:** stale open issues, a duplicate (#175/#176), and medium bugs open for 3 weeks.

**The serious finding: [#211](https://sdp.ms.wits.ac.za/innovation/sportsanalytics/pulls/211),
please merge this first.** Supabase automatically publishes your tables through a web API that
anyone holding the project's public "anon" key can call. On production:
- The roles that API uses had full read and write access to all 41 tables.
- The 39 row-level security rules (all named `service_role_all`) were set to allow everyone, so they
protected nothing.
- Two tables had no row-level security at all.

So anyone with that key could have read or changed user emails, login session tokens (enough to take
over an account), Google sign-in tokens and API key hashes. The API is live, but the key was never
committed to either repo or the web app, and nothing suggests it was used.

The fix is one migration: it removes the allow-all rules, turns row-level security on for every
table, and takes those roles' access away, including for future tables. It can't break the app,
because the API and Python jobs connect as the tables' owner and the photo storage uses the service
key, and both bypass these rules. I checked it read-only against production, and the SQL parses
cleanly.

**The rest of the database was fine:** private photo bucket, API keys stored only as hashes, and
deleting a user correctly removes everything they own.
